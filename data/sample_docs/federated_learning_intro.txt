Federated Learning: An Introduction

Federated learning is a machine learning approach that trains a shared global model across many decentralized devices or servers, each holding local data samples, without requiring those data samples to be exchanged or centralized. This stands in contrast to traditional centralized machine learning, where all training data is collected on a single server or data center before training begins. Federated learning was originally proposed by researchers at Google in 2016 as a way to train models on data generated by mobile phones, such as keyboard prediction models, without uploading users' private typing data to a central server.

The core motivation behind federated learning is privacy preservation. In many real-world settings, data cannot or should not leave its original location due to privacy regulations, competitive concerns, or sheer practical constraints. Hospitals, for example, may want to collaboratively train a diagnostic model using patient records from multiple institutions, but regulations such as HIPAA in the United States or GDPR in Europe make it difficult or illegal to share raw patient data across institutional boundaries. Similarly, banks may want to train fraud-detection models using transaction data from multiple branches or partner institutions without exposing sensitive financial records. Federated learning offers a way to benefit from a larger, more diverse dataset without centralizing the underlying data itself.

The typical federated learning process works as follows. First, a central server initializes a global model and sends a copy of it to a selected subset of participating clients, which might be mobile devices, hospital servers, or IoT sensors. Each client then trains the model locally using its own private data, typically for a small number of epochs, producing an updated set of model weights. Rather than sending their raw data back to the server, clients send only the updated model weights or gradients. The server then aggregates these updates from all participating clients into a new global model, most commonly using an algorithm called Federated Averaging, or FedAvg. This new global model is then redistributed to clients for the next round of training, and the process repeats over many rounds until the model converges.

FedAvg, introduced in the original 2016 paper by McMahan et al., works by taking a weighted average of the model parameters received from each client, where the weight given to each client is typically proportional to the amount of local data that client used for training. This simple averaging approach turns out to work surprisingly well in practice, even when client data is not independently and identically distributed, though performance can degrade significantly under extreme data heterogeneity across clients.

Federated learning introduces several technical challenges that do not arise in centralized training. One major challenge is statistical heterogeneity: because each client's local data reflects its own usage patterns or population, the data across clients is often non-IID, meaning it does not follow the same distribution. For example, in a flood forecasting application, sensors placed in different river basins will observe very different rainfall and water-level patterns depending on local geography and climate, making the federated averaging process less straightforward than in a setting with uniformly distributed data. Techniques such as FedProx, which adds a proximal term to the local training objective to limit how far local models can drift from the global model, have been proposed to address this heterogeneity.

A second major challenge is communication efficiency. Because federated learning involves repeatedly sending model updates between potentially thousands or millions of clients and a central server, communication bandwidth becomes a bottleneck, particularly for clients on slow or metered mobile connections. Approaches to reduce communication cost include model compression, where updates are quantized or sparsified before transmission, and reducing the frequency of communication rounds by allowing clients to perform more local training steps before synchronizing with the server.

A third challenge is system heterogeneity: participating clients may have vastly different computational capabilities, network conditions, and availability. A client might disconnect mid-training due to a lost network connection or a device being powered off, and the federated learning system must be robust to these dropouts without stalling the overall training process. Asynchronous federated learning variants have been proposed to handle this, allowing the server to aggregate updates as they arrive rather than waiting for all selected clients to respond.

Privacy in federated learning is not automatically perfect simply because raw data never leaves the client. Model updates themselves can leak information about the underlying training data through techniques such as gradient inversion attacks, where an adversary with access to a client's gradient update attempts to reconstruct the original training examples. To defend against this, federated learning is often combined with additional privacy-preserving techniques such as differential privacy, which adds carefully calibrated noise to model updates before they are sent to the server, and secure aggregation protocols, which use cryptographic techniques to ensure the server can only see the aggregated sum of client updates, never any individual client's update in isolation.

Federated learning has found applications well beyond its original mobile keyboard prediction use case. In healthcare, federated learning has been used to train models for medical image analysis across multiple hospitals without sharing patient scans. In environmental monitoring, federated learning enables distributed sensor networks, such as those used in flood forecasting or air quality monitoring, to collaboratively train predictive models using locally collected sensor readings while keeping raw sensor data on-site. In the financial sector, federated learning supports collaborative fraud detection across banks that are otherwise unwilling or unable to share raw transaction data due to competitive and regulatory concerns.

Despite its advantages, federated learning is not a universal solution. It introduces additional system complexity compared to centralized training, requires careful handling of non-IID data distributions, and generally requires more communication rounds to reach a given level of accuracy compared to centralized training on the same aggregate data, assuming that centralized training were possible. As a result, federated learning is best suited to settings where data centralization is genuinely infeasible or undesirable, rather than being adopted purely for its own sake.
